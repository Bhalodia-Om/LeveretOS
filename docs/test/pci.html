The PCI bus

Every device so far lived at a port number fixed by decades of convention. A network card does not. Finding out where it ended up is a lesson of its own.

Why this lesson exists

The keyboard is always at port 0x60. The timer is always at 0x40. Those numbers are burned into forty years of PC design and no driver has to discover them.

Expansion cards are different. They plug in, and the firmware assigns each one a block of ports at boot. Two identical machines can give the same card different addresses. So before you can write a single byte to a network card, you have to find it.

What PCI actually is A standard for how expansion cards describe themselves and get assigned resources. Every PCI device carries a small block of identification data called its configuration space, and the bus provides a uniform way to read that data without knowing anything about the device first.

Where devices live

A device's location is three numbers, and every PCI lookup needs all three.

The lessons only ever check function 0. Multi function devices exist, a combined network and modem card being the classic example, but the network card is on function 0 and scanning all eight would multiply the work by eight for nothing.

Two ports for the whole bus

PCI configuration space is not in the memory map. It is reached through two I/O ports, using the address and data pattern from the port I/O page.

These are 32 bit ports, which is why the lessons had to add inl and outl alongside the existing byte versions. PCI configuration is read in whole 32 bit words.

Packing the address word

This is the fiddly part of the lesson. Bus, device, function and offset all have to be squeezed into one 32 bit value, each in its own bit range.

Every field has a fixed home. Get a shift wrong and you read a different device entirely, or a different field of the right device, and the value you get back looks like plausible garbage.

What comes back at offset 0

The first 32 bit word of every device's configuration space holds two identification numbers, and together they say exactly what the device is.

Splitting them is the low half and high half of one 32 bit read, exactly the extraction pattern from the bits page.

The scan

With one function to read a config word, enumerating the whole bus is two nested loops and a check.

8192 reads happen in a fraction of a second, so the brute force approach is fine. A real OS would use the bridge information to skip buses that do not exist, but there is no need here.

The card was not what the lesson expected

The networking lessons were planned around the Intel e1000, a well documented card with plenty of reference material. The scan said otherwise.

Why this matters beyond the anecdote The whole point of a scan is to discover reality rather than assume it. Had the driver been written against the assumption, it would have configured registers on a card that was not there, and every read would have returned 0xFF with no clue why. The scan is what turned a hard bug into a five minute correction.

Finding one specific device

Listing everything is useful for a human. A driver wants a targeted search, which is the same walk stopping at the first match.

Returning a small struct rather than a sentinel value means the caller cannot mistake a valid location for a failure. Bus 0 device 0 is a real location, so there is no spare number to mean not found.

BAR0, the answer the driver needed

Knowing the card exists is not enough. The driver needs its port numbers, and those live in the configuration space at offset 0x10 in a Base Address Register.

The mask is not optional. An I/O BAR has its lowest bit set as a type marker, so the raw value is the real base port plus one. Every register access would land one byte off, which on this card means reading a completely different register.
