Guide / Talking to hardware

The GDT

A table that tells the CPU which regions of memory exist, who may touch them, and whether they hold code or data. GRUB set one up to get you booted, and now you replace it with your own.

What a segment is

Before paging existed, x86 divided memory into segments. A segment is a described region: it has a start address, a size, and a set of permissions. Every memory access the CPU makes goes through one.

The description lives in a table, and the CPU holds small registers that point into that table. When code runs, the CPU consults the code segment's entry. When a variable is read, it consults the data segment's entry.

The lessons make all three segments cover the entire 4 GB of address space, starting at zero. That sounds like it defeats the purpose, and in a sense it does. This is called a flat memory model, and it is deliberate.

Why flat segments Segmentation is the old way to protect memory and it is clumsy. Paging, built in lesson 15, does the same job far better. So the GDT is set up to get out of the way: three overlapping segments covering everything, no restrictions. It exists because the CPU insists on having one, and because interrupts cannot be set up without it.

The real reason this lesson exists

The OS behaves identically before and after the GDT lesson, which makes it feel pointless. It is not. Every interrupt gate in the IDT has to name a code segment for the handler to run in.

That 0x08 is a reference into the GDT. Without a GDT you control, there is nothing valid to point at, and the interrupt lesson could not happen. The GDT is groundwork.

The awkward split layout

Here is the part that makes the code look strange. A descriptor is eight bytes, and the fields inside it are not contiguous. The base address is split into three separate pieces, and the size limit into two.

This is a historical accident. The 80286 had 24 bit addresses and a smaller descriptor. When the 80386 extended everything to 32 bits, the new bits had to be bolted onto the end so old descriptors kept working. Forty years later you are still writing code to reassemble them.

Every line in that function is the same pattern: shift the value down so the piece you want reaches the bottom, then mask to keep only that piece. Exactly the technique from the bits page.

The access byte

One byte holds the permissions. The two values in the lessons, 0x9A and 0x92, differ by a single bit.

Bit 3 is the whole difference. Set means code, clear means data. Everything else is identical: present, ring zero, a normal segment, and readable or writable.

Read the bit meanings carefully Bit 1 means different things depending on bit 3. On a code segment it controls whether the code can be read as data, and code is never writable. On a data segment it controls whether the data can be written. Both of the lessons' segments set it, so code is readable and data is writable.

The granularity byte and the 4 GB trick

There is a problem with covering 4 GB. The limit field is only 20 bits, which reaches 1048575. Even as a byte count that is only 1 MB. So how does a 20 bit number describe 4 GB?

The granularity bit changes the unit. Clear, the limit counts bytes. Set, it counts 4 KB blocks. So the maximum limit of 0xFFFFF becomes 1048576 blocks of 4096 bytes, which is exactly 4 GB.

Handing the table to the CPU

The CPU does not want the table itself, it wants a tiny structure describing where the table is and how big it is. That structure gets loaded with a dedicated instruction.

The minus one is a common source of confusion. The field holds the offset of the last valid byte, not the number of bytes. Three entries of eight bytes is 24 bytes, and the last valid byte is at offset 23. Get this wrong by one and the CPU either rejects your final entry or reads one byte past the table.

Why loading it takes assembly

Building the table is ordinary C++. Activating it is not, because of one register the CPU refuses to let you write normally.

The data segment registers accept a plain move. CS, the code segment register, does not. Changing which code segment you are executing in is not a data operation, it is a change of execution context, and the only instruction that does it is a far jump.

The jump goes to the next line. Nothing moves in terms of program flow. The point is the side effect: passing through a far jump reloads CS with the selector you named.

Selectors, and where 0x08 and 0x10 come from

A selector is not an index, it is a byte offset into the table. That is why the numbers jump by eight rather than by one.

Entry one sits eight bytes into the table, so its selector is 0x08. Entry two sits sixteen bytes in, so 0x10. The low three bits of a selector hold flags for the privilege level, which is why real selectors are always multiples of eight.

Why entry zero must be null

The first descriptor is required to be all zeros and is never used. It is a deliberate trap.

A selector of zero is the value you get from an uninitialised variable. By making entry zero invalid, the CPU guarantees that accidentally using a zero selector raises a fault immediately rather than silently accessing whatever entry zero happened to describe. It turns a silent bug into a loud one.

All three entries, from gdt.cpp
gdt_set_entry(0, 0, 0, 0, 0); // null, required by the CPU gdt_set_entry(1, 0, 0xFFFFF, 0x9A, 0xCF); // code: 4 GB, ring 0, executable gdt_set_entry(2, 0, 0xFFFFF, 0x92, 0xCF); // data: 4 GB, ring 0, writable
Both real segments start at 0 and cover everything. They overlap completely, which is the flat model. The only difference is the access byte.
