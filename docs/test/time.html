Guide / Talking to hardware

Timer and clock

Two completely separate chips that both involve time. One is a metronome for measuring intervals, the other is a calendar that remembers the date while the machine is off.

Two chips, two jobs

Confusing these is easy because both are about time, but they answer different questions and neither can do the other's job.

The PIT cannot tell you the date, it has no idea what a date is. The RTC cannot give you a steady interrupt, it just holds the current time. So the lessons use both.

How the PIT produces a steady tick

The chip has a fixed input frequency it cannot change, roughly 1.19 MHz. You cannot ask it for 100 interrupts per second directly. Instead you give it a divisor, and it counts down from that number, firing each time it reaches zero.

So the rate is the base frequency divided by your divisor. Working out the divisor is one division, and the lessons do it at the top of timer_init.

Where 1193182 comes from The original PC derived its timer clock from the same crystal used for video timing, chosen so that colour television signals worked. The number is 315/22 MHz divided by 12, and it has been carried forward unchanged for forty years. Nobody would pick it deliberately today.

The command byte

Before sending the divisor you send one byte describing how the chip should behave. It packs four separate settings, which makes it a good example of a bit field in the wild.

Bits 5 and 4 are the interesting pair for this page. They tell the chip that a 16 bit value is arriving as two separate 8 bit writes, low byte first. The chip is announcing the byte order it expects, which is the hardware convention covered on the byte order page.

Counting ticks

The handler is deliberately tiny. It increments a counter and acknowledges the interrupt, and that is all.

At 100 Hz this runs a hundred times a second, forever, for as long as the machine is on. Anything slow in here would steal time from everything else, which is why counting is the entire job.

Turning ticks into seconds

A tick count is only meaningful if you know the rate, which is why the lessons store the frequency alongside the counter.

Dividing the tick count by the frequency gives seconds since boot. Keeping the frequency in a variable rather than hardcoding 100 means the arithmetic stays correct if the rate ever changes.

The RTC, a different chip entirely

The real time clock sits on a small battery so it keeps running when the machine is off. It holds the wall clock time and date, and it is reached through the address and data port pattern from the port I/O page.

The register numbers are not sequential, because the odd numbers in between hold alarm values nobody uses. You cannot derive them, they are simply what the chip designers chose.

BCD, the gotcha that bit the lessons

Here is the thing that produces wrong times and confuses everybody the first time. The RTC does not return binary numbers. It returns binary coded decimal, where each nibble holds one decimal digit.

So the byte 0x42 means forty two, not sixty six. Read it as binary and you get a number that is wrong in a way that looks almost plausible, which is the worst kind of wrong.

Why BCD at all The chip was designed to drive a digital display directly. With one digit per nibble, showing the time needs no arithmetic, you just map each nibble to a glyph. Convenient for 1984 hardware, inconvenient for software that wants to do maths on the value.

Checking the format rather than assuming

Most machines return BCD, but the chip can be configured for binary. Rather than assume, the lessons read a status register and check.

The logic reads oddly because the bit means the opposite of what you might expect. Bit 2 set means binary mode, so BCD is indicated by the bit being clear, hence the negation.

What the lessons skipped

The RTC has genuine subtleties that a narrow scope can ignore, and it is worth knowing they exist rather than discovering them later as bugs.
