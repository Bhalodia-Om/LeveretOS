Guide / Getting online

The NE2000 card

The network card has its own memory that your CPU cannot address, and only sixteen registers to reach all of it. Both of those constraints shape every line of the driver.

An old, simple design

The card the PCI scan found is a Realtek RTL8029, compatible with the NE2000 from the 1980s. That age is genuinely helpful: it uses the port I/O the OS already has rather than memory mapped registers, so no new mechanism is needed.

The tradeoff is that everything moves through a narrow window rather than being directly addressable, which is what makes the driver's shape unusual.

The card has its own RAM

This is the central fact to understand. The card contains 16 KB of memory that is not part of your machine's address space at all. Packets live in there, not in your RAM.

So sending a packet means copying it from your memory into the card's memory, and receiving means copying the other way. There is no shared buffer and no pointer you can dereference.

The warehouse analogy The card's RAM is a warehouse you cannot walk into. You tell the clerk which shelf to start at and how many items you want, then receive them one at a time through a single service window. The window is one port, and this arrangement is called remote DMA.

Sixteen registers, and pages

The card exposes only sixteen port offsets, which is not enough for everything it needs to expose. The solution is to overlay several sets of registers at the same offsets and switch between them.

Two bits of the command register select which page is visible. So offset 0x07 is the interrupt status on page 0 and the current receive page on page 1, and which one you get depends on what you last wrote to the command register.

The mistake this invites Forgetting which page is selected means reading or writing a completely different register than intended, with no error. The driver always switches back to page 0 immediately after a page 1 access, so the default state is predictable.

Remote DMA

Moving bytes between your memory and the card's is a three step protocol: say where, say how many, then stream them through one port.

The address and count are each 16 bit values split across two 8 bit registers, the low byte first convention from the byte order page. The 0 and 1 suffixes in the register names mean low and high.

The bug that scrambled the MAC

Reading the card's MAC address was the first real use of remote DMA, and it produced a wrong answer in an instructive way.

How it was diagnosed The clue was that the last three bytes were correct while the first three were scrambled. Random garbage would have corrupted all six. A partial, structured error pointed at an alignment or stride problem rather than a wrong address, which narrowed it to the transfer width.

The doubled PROM

Even with the right transfer width, the MAC does not come out of the card in six consecutive bytes.

The card duplicates each of the first sixteen bytes of its identification memory, so MAC byte i sits at offset i * 2. The driver reads twelve bytes and keeps every other one.

Dividing up the card's memory

The card's RAM has to hold both outgoing and incoming packets, so the driver splits it into two regions measured in 256 byte pages.

A full Ethernet frame is 1514 bytes, which spans six pages, so the transmit region needs at least that much. The receive ring gets everything else.

The receive ring

Incoming packets go into a circular region of the card's memory. Two pointers track it, one moved by the card and one by the driver.

The gap between the two pointers is the unread packets. When they meet, the ring is empty. If the card's pointer catches up to the driver's from behind, the ring is full and packets get dropped.

Every received packet has a header

The card prepends four bytes to each packet it stores, and those bytes are what make walking the ring possible.

The next page pointer is the important one. Packets are variable length, so the only way to find where the following packet begins is to read it from the header of the current one.

Sending a frame

Transmitting is two distinct phases: copy the frame into the card, then tell the card to send what is sitting there.

Why the loopback test failed

The plan was a self contained test: put the card in internal loopback so a sent frame comes straight back, proving both directions without needing another machine. It did not work, and the reason is worth knowing.

So transmit was verified a different way, by capturing what left the card, and receive had to wait for the ARP lesson where a real gateway sends a genuine reply.

Verifying transmit honestly QEMU can write every frame crossing the virtual network into a capture file. The captured bytes matched the frame the OS built exactly, including the zero padding to the 60 byte minimum. That is real proof the transmit path works, even though the OS itself could not observe it.
