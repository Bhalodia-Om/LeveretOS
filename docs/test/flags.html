Flags and bit fields

Hardware rarely wants one number. It wants a dozen yes or no answers crammed into a single byte, and each position means something completely different.

Why cram settings together

Imagine you are designing a chip in the 1980s. You want the programmer to be able to say "this memory region is present, it is writable, and only the kernel may touch it". That is three separate yes or no answers.

You could give each one its own byte, but bytes on a chip cost real money and real wires. So instead you define one byte and declare that bit 0 means present, bit 1 means writable, bit 2 means user accessible. Now three settings fit in eight bits, with room for five more.

The catch is that the resulting number looks arbitrary. When you read outb(PIT_COMMAND, 0x36) in the timer code, 0x36 is not a quantity. It is four separate decisions packed together, and the only way to read it is to split it back into bits.

The mental move When you see a hex constant written to hardware, stop reading it as a number. Convert it to binary and ask what each position means. The datasheet tells you the meanings, and this page shows you the pattern.

A real one, the GDT access byte

The GDT lesson writes two values, 0x9A for the code segment and 0x92 for the data segment. They differ by a single bit. Click the flags below and watch which byte you land on.

Only bit 3 separates them. Everything else is identical: present, ring 0, normal segment, readable or writable. That is why the lesson comment says the two values differ by one bit, and now you can see exactly which one.

Fields wider than one bit

Sometimes a setting has more than two possible values, so it needs more than one bit. Two bits give you four choices, three bits give you eight. The datasheet describes these as a range, like "bits 5 to 4 select the access mode".

The PIT command byte from the timer lesson is a good example. It packs a channel number, an access mode, an operating mode and a format flag into eight bits.

0x36 taken apart, the PIT command byte
0x36 = 0 0 1 1 0 1 1 0 | | | | | | | | | +-- bit 0 : 0 = the divisor is in binary, not BCD | | | +------ bits 3-1 : 011 = mode 3, square wave, fires like a metronome | | +---------- bits 5-4 : 11 = send the 16 bit divisor as two 8 bit writes, low byte first +-+------------ bits 7-6 : 00 = channel 0
Four unrelated settings, one byte. This is why the lesson comment spells out each bit range.

Notice the bit ranges are written high to low, "bits 5-4" rather than "bits 4-5". That is the convention everywhere in hardware documentation, because binary is written with the most significant bit on the left. It matches how you would read the number.

Why the code uses names, not numbers

Every lesson defines constants rather than writing raw hex at the call site. The NE2000 driver is the clearest case.

From the NE2000 driver
#define CR_STOP 0x01 #define CR_START 0x02 #define CR_RDMA_RD 0x08 #define CR_PAGE0 0x00 #define CR_PAGE1 0x40 // then, at the call site: outb(io_base + NE_CR, CR_RDMA_RD | CR_START);
That last line reads as an instruction: start a remote DMA read, with the card running. Written as 0x0A it would read as nothing at all.

The OR combines them, exactly as covered on the bits page. Each constant contributes its own bit, none of them collide, and the result is a single byte the chip understands.

Reading a field back out

Writing flags is easy, you OR them together. Reading them is where the mask comes in. To ask "is the card finished with the DMA transfer", the driver checks one bit out of the status register.

Testing a single flag
#define ISR_RDC 0x40 // bit 6, remote DMA complete while ((inb(io_base + NE_ISR) & ISR_RDC) == 0) { }
Read the whole byte, mask off everything except bit 6, and loop while the result is zero. The other seven bits could be anything and this still works.

This is why masking matters so much. The status register holds eight unrelated pieces of news at once. Without the mask you would be testing all of them together and the condition would be meaningless.

Clearing flags by writing ones

Here is a piece of hardware behaviour that catches everybody. On many chips, including the NE2000, you clear a status bit by writing a 1 to it, not a 0. It feels backwards.

The logic from the chip's side is that a status register is a set of latches. Writing a 1 means "I have seen this one, reset it". Writing a 0 means "leave this one alone". So the driver writes 0xFF to clear every pending status bit at once.

From the NE2000 reset
outb(io_base + NE_ISR, 0xFF); // clear all interrupt status bits
All ones, meaning acknowledge everything. Writing 0x00 here would clear nothing.
Always check the datasheet direction Whether a register is write-1-to-clear, write-0-to-clear, or plain read and write is a per-register decision made by whoever designed the chip. There is no universal rule, which is exactly why driver code is full of comments explaining what each write is for.

The same idea at every layer

Bit fields are not just a hardware register thing. Once you can read them, you will spot the pattern everywhere in the lessons.

WhereWhat is packed
GDT access bytepresent, privilege level, code or data, readable or writable
Page table entrya physical address in the top 20 bits, flags in the low 12
PCI config addressan enable bit, bus, device, function and register offset in one 32 bit word
PIC mask registerone bit per interrupt line, 1 means blocked
Heap block headera size, plus a free or used flag

The page table entry is the most elegant one. Because pages are 4 KB aligned, the low 12 bits of a page address are always zero, so they would be wasted. The designers put the flags there instead. The paging page covers how that works.
