C++ without a system

Writing a kernel means writing C++ with nothing underneath it. No standard library, no operating system, no safety net. Several familiar things stop working and a few unfamiliar ones become essential.

What you lose

Normally your program sits on top of an operating system that provides a huge amount for free. In a kernel there is nothing below you, so all of that vanishes at once.

This is what freestanding means. The build script says so explicitly, and each flag turns off a feature that would otherwise expect a system to be there.

Fixed width integer types

In ordinary C++ you write int and do not think about it. In a kernel you almost never write int, because the exact number of bits matters enormously.

A hardware register is precisely 8 or 16 or 32 bits wide. A struct describing a GDT entry has to match a layout the CPU decided on. If your field is the wrong size, every field after it shifts and the whole thing is garbage. So the lessons use types that state their width.

TypeBitsTypical use in the lessons
uint8_t8one byte, a port value, a MAC byte, a scancode
uint16_t16a port number, an EtherType, a VGA screen cell
uint32_t32an address, a page table entry, a PCI config word
size_t32 herea count or a length, widens automatically on 64 bit

The u means unsigned, no negative values. That matters for addresses and bit patterns: bit 31 of a signed 32 bit number is the sign bit, so setting it would make the number negative rather than large. The paging code sets exactly that bit to enable paging, which is why it uses unsigned types throughout.

Structs as a memory layout

A struct in a kernel is often not a convenience container. It is a description of bytes that already exist somewhere, or that hardware will read.

When the PMM reads GRUB's memory map, GRUB has already written those bytes into RAM. The struct just tells the compiler how to interpret them.

No copying happens. The cast says "treat the bytes at this address as a MultibootInfo", and reading a field compiles to a read at the right offset. This is the standard way to work with data another piece of software or hardware laid down.

Packed, and why padding would ruin everything

Compilers normally insert invisible padding between struct fields so each one sits on a convenient address boundary. That makes access faster and is completely fine, until the struct has to match an exact hardware layout.

What padding would do to a GDT entry
struct GdtEntry { uint16_t limit_low; // 2 bytes uint16_t base_low; // 2 bytes uint8_t base_mid; // 1 byte uint8_t access; // 1 byte uint8_t granularity; // 1 byte uint8_t base_high; // 1 byte }; // should be exactly 8 bytes // without packed, a compiler may quietly make it 10 or 12 bytes // by inserting gaps. The CPU then reads the wrong fields and // the segment description is nonsense.
__attribute__((packed)) forbids the gaps. Every field sits exactly where the CPU expects it.

You will see packed on every struct in the lessons that describes something outside your own program: GDT entries, IDT entries, the multiboot structs. Structs used only internally, like the heap's block header, do not need it.

Volatile

This one is subtle and causes real bugs. The compiler is allowed to optimise away reads it thinks are pointless. If you read a variable twice in a loop and nothing in the loop changes it, the compiler may read it once and reuse the value.

That is a sound assumption for normal variables and completely wrong for anything an interrupt handler touches, because the handler changes it behind the compiler's back.

The keyboard driver has the same situation. line_ready is set inside the interrupt handler and read by read_line, which sits in a loop waiting for it. Without volatile the compiler could hoist the read out of the loop and spin forever on a stale value.

The symptom A missing volatile usually shows up as a hang, or as code that works at one optimisation level and breaks at another. Nothing crashes and no error appears, which makes it genuinely nasty to track down.

Pointers as plain addresses

In a kernel a pointer is just a number that happens to be a memory address, and you write them out by hand all the time. The VGA driver is the clearest example.

From the VGA driver
static uint16_t* const VGA_MEMORY = reinterpret_cast<uint16_t*>(0xB8000);
0xB8000 is not a variable anywhere. It is a fixed address the video hardware watches. The cast says treat that address as an array of 16 bit cells.

After that line, VGA_MEMORY[0] is the top left character cell on screen. Writing to it changes the display. There is no function call and no driver in between, you are writing to a place the hardware is reading from.

Output parameters

With no std::pair or tuples available, and functions only able to return one value, the lessons hand back extra results by writing through pointers the caller supplies.

The caller creates the storage, passes its address, and the function fills it in. The & in front of a variable means "the address of this", which is a different operator from the bitwise AND between two values covered on the bits page.

Static and extern

These two keywords control who can see a name, and the lessons use them deliberately.

static at file scope means private to this file. The NE2000 driver's io_base is static, so no other file can reach in and change the card's port address. It is the closest thing to encapsulation available here.

extern means this exists somewhere else, do not create another one. The VGA header declares extern size_t cursor_row; so every file shares one cursor position rather than each getting its own copy.

extern "C" and name mangling
extern "C" void gdt_flush(uint32_t gdt_ptr_address);
C++ normally decorates function names to allow overloading, turning gdt_flush into something like _Z9gdt_flushj. The assembly file only knows the plain name, so extern "C" turns the decoration off.

Every function that crosses between C++ and assembly needs this: gdt_flush, interrupt_handler, kernel_main, and the interrupt stubs. Forget it and the linker cannot find the symbol.

Inline assembly

Some CPU instructions have no C++ equivalent. You cannot ask C++ to read a control register or load the interrupt table, so those few lines are written in assembly inside the C++ file.

Reading a port, from io.h
static inline uint8_t inb(uint16_t port) { uint8_t result; asm volatile ("inb %1, %0" : "=a"(result) : "Nd"(port)); return result; }
The quoted part is the instruction. After the first colon are outputs, after the second are inputs. "=a" means the result comes back in the accumulator register, "Nd" means the port can be a constant or go in the DX register.

The constraint letters look cryptic but there are only a handful in the whole project. Note that volatile appears here too, for the same reason as before: this instruction has a side effect on hardware, so the compiler must not decide it is unnecessary and drop it.

Worth knowing "=a" means the accumulator register, but which one depends on the variable's type. With a uint8_t it is the 8 bit AL, with a uint32_t it is the full 32 bit EAX. Same constraint, different register, chosen automatically from the type. That is why inb and inl look nearly identical.
