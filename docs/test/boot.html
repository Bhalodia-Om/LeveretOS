Boot and the linker

Before a single line of your C++ runs, something has to load it into memory and give it a stack. This page is about that handover, and about the file that decides where everything lands.

Who starts what

When a machine powers on, the CPU does not know what an operating system is. It runs firmware from a chip on the motherboard, that firmware finds a bootable disc, and a bootloader takes over from there. Only then does your code get a turn.

The lessons use GRUB as the bootloader, so there are four players in the handover.

The important thing to notice is that by the time kernel_main runs, a great deal has already happened that you did not write. The CPU is already in 32 bit protected mode, because GRUB switched it there. Memory has already been surveyed. Your kernel has already been copied to a specific address. All of that is GRUB doing its job.

The multiboot header, how GRUB recognises a kernel

GRUB will not load an arbitrary file. It scans the first few kilobytes looking for a magic number, a specific pattern that says "this is a kernel that speaks multiboot". If it does not find it, it refuses to boot.

The checksum is the part that looks strange. GRUB adds the magic, the flags and the checksum together and requires the result to be zero. So the checksum is defined as the negative of the other two added up. It is a cheap way for GRUB to confirm it found a real header rather than three bytes that happened to look right.

Why the header must come first GRUB only scans the beginning of the file. The linker script puts the .multiboot section at the start of .text for exactly this reason. Bury it deeper and GRUB never sees it.

Sections, and what the linker is actually doing

A compiled program is not one undifferentiated blob. The compiler sorts everything into sections by what kind of thing it is, and the linker decides where each section sits in the final binary.

The distinction between .data and .bss is worth pausing on, because it saves real space. A variable initialised to a specific value has to have that value stored in the file. A variable initialised to zero does not, the loader can simply zero the memory. So .bss takes up address space but almost no file space.

That is why the PMM's bitmap costs nothing on disc. It is a 128 KB array in .bss, and the heap's 1 MB buffer is the same. Neither one inflates the ISO.

Reading the linker script

The linker script is the file that lays all this out. It is a small language of its own, and the lessons use only a handful of its features.

The . is the key idea. It is a cursor holding the current output address. Setting it to 1M starts the layout at 1 megabyte. As each section is placed, the cursor advances past it. So by the end of the script, the cursor sits just past everything, and naming that position gives you the end of the kernel.

Why 1 MB The first megabyte of memory on a PC is a museum of legacy hardware: the video buffer, BIOS data, memory mapped devices. Loading above it avoids landing on top of any of that.

kernel_end, the symbol that protects the kernel

That last line of the linker script exists for one purpose. The physical memory manager needs to know which memory it must never hand out, and the answer is "everything the kernel occupies". The linker knows where that ends, so it tells the code.

There is no variable called kernel_end anywhere in the C++ source. The extern declares that the symbol exists elsewhere, and the linker provides it at link time. Taking its address gives you the number the script computed.

Why the first code must be assembly

boot.s is short, and everything in it is something C++ cannot do.

The stack is the blocker. C++ needs a stack for local variables and function calls, but setting the stack pointer is a function call's worth of work. You cannot bootstrap a stack from a language that assumes one exists. So assembly points the stack pointer at a reserved block, and from that instruction onward C++ is viable.

The stack grows downward esp is set to stack_top, the high address, not the bottom. Each push moves it down toward stack_bottom. Point it at the bottom instead and the first push walks off into whatever sits below, corrupting memory with no error message and no obvious trace of where it went wrong.

Passing GRUB's memory map along

GRUB leaves a pointer to its information structure in the ebx register. That register is not preserved forever, so boot.s has to hand it over immediately.

On 32 bit x86, function arguments arrive on the stack. Pushing ebx just before the call means the value appears as kernel_main's first parameter. That is the entire mechanism behind the multiboot_info_addr argument, and it is why the PMM can read GRUB's memory map at all.

The hang at the end

The last three instructions in boot.s only run if kernel_main somehow returns, which it should not because the shell loops forever. It is a safety net.

Stopping safely
.hang: cli ; disable interrupts, so nothing wakes us hlt ; halt the CPU until an interrupt arrives jmp .hang ; if something wakes it anyway, halt again
cli then hlt is the standard way to stop a CPU dead. The jump back exists because a non maskable interrupt can resume execution past hlt, and without the loop the CPU would run off into whatever bytes follow.

The same pattern appears in the exception handler in idt.cpp. When the CPU hits an unrecoverable fault, the handler prints what happened and then parks in exactly this loop, because continuing would be worse than stopping.
