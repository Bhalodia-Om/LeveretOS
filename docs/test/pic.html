Guide / Talking to hardware

The PIC

A chip that collects interrupt requests from every device and passes them to the CPU one at a time. Out of the box its numbering collides with CPU exceptions, so the first job is moving it out of the way.

Why a middleman exists

The CPU has a single interrupt request pin. There are far more than one device wanting to interrupt. Something has to sit in between, collect the requests, prioritise them and feed them through one at a time.

That chip is the Programmable Interrupt Controller. It handles eight lines, which was not enough even in the 1980s, so PCs have two of them wired together.

The slave does not talk to the CPU directly. Its output feeds into the master's line 2, so a request from the slave arrives at the CPU as if it came through the master. That detail matters later when acknowledging interrupts.

Which line is which IRQ0 is the timer and IRQ1 is the keyboard, both on the master, which is why the lessons only ever touch those two. IRQ2 is not a real device, it is where the slave plugs in.

The collision that forces a remap

By default the PIC delivers its eight master lines as interrupt numbers 8 through 15. That range is already taken.

So a keypress on IRQ1 arrives as interrupt 9, which the CPU also uses for a coprocessor exception. The dispatcher cannot tell whether a genuine fault occurred or somebody pressed a key. Worse, a timer tick on IRQ0 arrives as interrupt 8, the double fault.

The fix is to tell the PIC to use different numbers. It is programmable, which is what the P stands for, so you can move its whole range up past the 32 reserved exceptions.

Initialisation command words

Reprogramming the PIC means sending four bytes in a fixed order. The chip is from an era when configuration was a sequence rather than a set of independent registers, so the order is not optional.

Every byte goes to both chips, because both need configuring. The only differences are ICW2, where each chip gets its own base number, and ICW3, where one is told it has a slave and the other is told it is one.

The order is part of the protocol After ICW1 the chip is waiting for the rest of the sequence. Sending them out of order, or skipping one, leaves it half configured with no error reported. The lessons send all four to both chips in strict order for exactly this reason.

Masking, and the bug it caused

After the four command words comes a fifth write, the interrupt mask. One bit per line, and the polarity is the opposite of what most people guess.

A set bit means blocked. So 0xFF blocks everything and 0x00 allows everything. The lessons use 0xFC on the master, which is 11111100: bits 0 and 1 clear, so the timer and keyboard are allowed and the rest are blocked.

This is where lesson 11 produced a real crash, and it is worth understanding because the failure mode is so unhelpful.

The rule that came out of it Never unmask an interrupt line before its IDT gate has a handler. The lessons masked the timer with 0xFD until lesson 13 added a timer handler, then changed to 0xFC. The ordering is not stylistic, it is what stops the machine rebooting.

End of interrupt

The PIC does not send another interrupt on a line until you tell it the previous one is finished. That acknowledgement is one byte to a command port, and forgetting it is the most common PIC mistake.

The symptom is distinctive. Everything works exactly once. One keypress registers, then the keyboard appears dead, because the PIC is still waiting to hear that the first interrupt was handled.

Why the slave needs two acknowledgements

The one piece of genuine subtlety in the EOI code. Because the slave's output passes through the master's line 2, an interrupt from the slave was handled by both chips.

So both need telling. The lessons handle this with a single comparison: if the IRQ number is 8 or higher it came from the slave, so acknowledge the slave first and then always acknowledge the master.

In practice the lessons only ever use IRQ0 and IRQ1, both on the master, so the slave branch never runs. It is written correctly anyway, because getting it wrong later would be a confusing bug to find.

The full sequence in one place

Nine port writes configure the entire interrupt system. Here is what each one accomplishes.

WritePortValueMeaning
ICW10x200x11master: begin initialisation, expect an ICW4
ICW10xA00x11slave: same
ICW20x210x20master: deliver my lines starting at interrupt 32
ICW20xA10x28slave: deliver my lines starting at interrupt 40
ICW30x210x04master: a slave is attached on line 2
ICW30xA10x02slave: I am attached to the master's line 2
ICW40x210x01master: use 8086 mode
ICW40xA10x01slave: same
mask0x210xFCmaster: allow only lines 0 and 1, the timer and keyboard
mask0xA10xFFslave: block everything, nothing there is used

Note which port each value goes to. ICW1 goes to the command port, everything after it goes to the data port. That is another piece of the chip's protocol: once initialisation starts, the data port is where the rest of the sequence is expected.
