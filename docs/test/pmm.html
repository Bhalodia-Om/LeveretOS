Guide / Managing memory

Physical memory

Before the OS can hand out memory it has to know what memory exists, and which parts it is allowed to touch. That bookkeeping is one bit per 4 KB chunk of RAM.

Not all memory is RAM

A naive assumption would be that a machine with 128 MB has 128 MB of usable addresses starting at zero. It does not. The address space is a patchwork, and writing to the wrong part of it does anything from nothing at all to breaking the display.

There is no way to work this out from first principles, it varies by machine. So the OS asks. GRUB surveyed memory during boot and left a list behind, which is exactly what that memory map flag in the multiboot header was requesting.

Where the list comes from GRUB asked the firmware, which knows because the chipset tells it. Your kernel receives the finished list as a pointer in ebx, handed along by boot.s as described on the boot page.

Frames, not bytes

Tracking every individual byte would need a byte of bookkeeping per byte of RAM, which is absurd. So memory is divided into fixed size chunks called frames, and the allocator deals only in whole frames.

4096 bytes is not arbitrary. It is the page size the CPU's paging hardware uses, so choosing the same size means a frame maps exactly onto one page later. The paging lesson depends on that alignment.

One bit per frame

The bookkeeping is a bitmap: a long row of bits where each bit answers one question, is this frame in use. One bit is the smallest possible answer, which makes the whole structure remarkably cheap.

128 KB to track 4 GB of RAM is a ratio of about 1 to 32000. That efficiency is the entire reason to use a bitmap rather than a list.

Finding a frame's bit

The bitmap is an array of 32 bit words, but you think in terms of frame numbers. Converting between the two is one division and one remainder, and this pattern appears in all three helper functions.

Divide by 32 to find which word holds the bit, then take the remainder to find its position inside that word. A frame number of 100 lives in word 3 at bit 4, because 100 divided by 32 is 3 with 4 left over.

These three lines are the set, clear and test operations from the bits page, applied to a real structure. If they read naturally now, the rest of this page is straightforward.

Start pessimistic, then free what is real

The initialisation order looks backwards at first. Everything is marked used, then usable regions are freed. Doing it the other way round would be a security hole.

The reasoning is about what happens to memory the map does not mention. Starting from all used means anything unlisted stays reserved and is never handed out. Starting from all free would mean unlisted memory is handed out by default, which could include memory mapped devices.

Fail safe, not fail open This is a general principle worth carrying forward. When you cannot enumerate every case, default to the restrictive answer and explicitly permit what you have verified. The reverse defaults to permitting things you never checked.

Walking GRUB's list

The memory map is a list of variable length entries, which makes stepping through it slightly unusual. You cannot index it like an array.

Each entry carries its own size so the loop can find the next one. The plus four accounts for the size field itself not being counted in the size it reports, which is a genuine quirk of the multiboot specification rather than a bug.

Protecting the kernel from itself

After freeing the usable regions there is a problem. The kernel is sitting in one of those regions, so its own frames were just marked as available.

Without that second pass, the first call to alloc_frame would return address zero and the paging code would build its page directory directly on top of the kernel's code. The symptom would be immediate and incomprehensible.

Handing out a frame

The allocator is a linear search for the first clear bit. Simple, and slow in a way that does not matter yet.

Returning the frame number multiplied by the frame size converts a bit position back into a real physical address. Frame 3 becomes address 12288, and that is what the caller can actually use.

Why the numbers look the way they do

Running the mem command in the lessons shows figures that surprise people. Both of the surprising ones have straightforward explanations.

The bitmap is sized for 4 GB because that is the most a 32 bit address can reach. It does not mean the machine has 4 GB, only that the allocator could cope if it did.

What this allocator deliberately is not

It is worth being clear about the limits, because the next lesson builds a different allocator on top for exactly these reasons.

LimitationConsequence
only whole 4 KB framesasking for 12 bytes wastes 4084 of them, which is why the heap exists
linear searchfinding a frame gets slower as memory fills. Fine for a handful of allocations, wrong for thousands
no contiguous allocationthere is no way to ask for four frames in a row, which a real driver would need for DMA buffers
no ownership trackingthe bitmap knows a frame is used but not by whom, so nothing detects a double free

Each of these is a reasonable trade for a teaching OS. The point of the PMM is to be the one thing that knows which physical memory is real and available, and it does that job correctly.
