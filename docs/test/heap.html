Guide / Managing memory

The heap

Writing your own malloc and free. The PMM hands out 4 KB frames, which is hopeless when you want twelve bytes, so this layer cuts them down to whatever size was actually asked for.

The problem with fixed buffers

Every buffer in the OS up to this point had its size decided when the code was compiled. The keyboard line buffer is 128 bytes, the shell command buffer is 128 bytes, the receive frame buffer is 1600 bytes. All chosen in advance.

That works until you need something whose size you only learn while running. A webpage might be 8 KB one time and 40 KB the next, and no single fixed number is right.

The PMM already hands out memory, but its unit is far too coarse to use directly. Asking for twelve bytes and receiving 4096 wastes 4084 of them, and doing that repeatedly exhausts memory almost immediately.

The lumber yard analogy The PMM is a yard that only sells full pallets. The heap is the shop that buys a pallet and cuts you the exact plank you asked for. Same wood, different unit of sale.

Where the memory comes from

The lessons take the simplest option available: one large static array, reserved at compile time.

Because it is uninitialised it lands in .bss, so it costs a megabyte of address space and nothing at all in the ISO. The same trick the PMM bitmap uses, explained on the boot page.

The block header

The interesting design decision. Rather than keeping a separate table of allocations, each block carries its own bookkeeping in the bytes immediately before the usable space.

So the heap is a chain: header, bytes, header, bytes, header, bytes, running the length of the region. Following the next pointers walks the whole thing.

How a pointer becomes a header

This is the trick that makes the whole design work. free receives only a pointer and has to find the block's bookkeeping. Because the header sits at a fixed distance, that is one subtraction.

No lookup table, no search, no registry of allocations. The header is always exactly sizeof(BlockHeader) bytes before the pointer you handed out, so arithmetic finds it instantly.

Setting up

Initialisation lays a single free block over the entire region. One header at the start, and everything after it is usable.

The usable size is the region minus one header, because those first twelve bytes are the header itself and cannot also be handed out.

First fit allocation

Finding a block is a walk down the chain, taking the first one that is free and large enough. Not the best fit, not the smallest adequate one, just the first.

The split guard

The condition deciding whether to split is worth its own look, because the plus one prevents a real problem.

Without room for a header plus at least one usable byte, splitting would create a block that can never hold anything, or worse, compute a negative size that wraps to an enormous number because the type is unsigned.

Unsigned subtraction bites hard size_t is unsigned, so 10 - 12 is not negative two, it is roughly four billion. A block claiming that size would be handed out on the next allocation and the caller would write far past the end of the heap. The guard is what stops that arithmetic ever happening.

Freeing and merging

Freeing is marking a flag, plus one attempt to merge with the block after it. Merging matters more than it looks.

Without merging, the heap gradually fills with small free blocks that are individually too small to be useful. That is fragmentation, and it means an allocation can fail even when the total free space is plenty.

Forward only, and what that costs

The merge looks at the next block but never the previous one. That is a deliberate simplification with a visible consequence.

Merging backwards would need either a previous pointer in every header, making each one larger, or a full walk from the start to find the preceding block. The lessons took neither, accepting some leftover fragmentation instead.

Watching it happen

The heaptest command runs two allocations and two frees, printing usage at each step. Every number has an explanation.

That final 24 rather than 12 is the forward only merge showing itself. It is not a bug, it is the documented consequence of the simplification, and seeing it in the output is a good sanity check that the merge logic works the way it was described.

What a production allocator adds

The lessons' heap is correct and small. Real allocators differ in ways worth knowing about.

MissingWhy it matters
growing on demandthe region is a fixed 1 MB. A real heap asks the PMM for more frames and maps them in with paging, which is why paging comes first
backward mergingleftover headers accumulate, slowly fragmenting the heap over many allocate and free cycles
alignment guaranteesreturned pointers are not aligned to any particular boundary, which some types and some hardware require

double free detectionfreeing the same pointer twice corrupts the chain silently, with the damage appearing much later somewhere unrelated

None of those are needed to make the networking code work, which is what the heap was built for. Knowing they are absent is what stops them becoming mysterious bugs later.
