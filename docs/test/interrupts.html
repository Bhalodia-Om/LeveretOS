Guide / Talking to hardware

Interrupts and the IDT

A mechanism for the CPU to stop what it is doing, run a function you nominated, and resume exactly where it left off. It is how the OS learns that anything happened.

Two different reasons to interrupt

Both arrive through the same table, but their causes could not be more different, and the lessons handle them separately.

Exceptions are the CPU complaining about your code. Hardware interrupts are devices reporting news. The dispatcher in idt.cpp tells them apart purely by number: anything below 32 is an exception, and the lessons put the keyboard and timer at 32 and 33.

Why exceptions come first The interrupt lesson sets up all 32 exception handlers before touching hardware interrupts at all. That is deliberate. Once exceptions report themselves by name, every later mistake tells you what went wrong instead of silently rebooting the machine.

The table the CPU consults

When an interrupt arrives, the CPU needs to know which function to run. It looks up the interrupt number in a table of 256 entries, each one called a gate.

Notice the handler's address is split in half, with the selector and flags sitting in between. Same historical accident as the GDT: the 16 bit original had a smaller gate, and the extra address bits were appended when addresses grew to 32 bits.

What the CPU pushes before your handler runs

This is the part that makes interrupt handlers unusual. Before jumping to your code, the CPU pushes enough information onto the stack to resume afterwards.

That frame is why a handler cannot end with an ordinary ret. A normal return pops one address. An interrupt return has to pop three values and restore the flags register, which is a different instruction entirely.

The error code inconsistency

Some exceptions push an extra value describing what went wrong, and some do not. The CPU does not offer a choice about this, it is fixed per exception number.

That inconsistency is a problem, because the common handler needs one predictable stack layout. The fix is to give the no error code cases a fake one.

Now every stub has pushed exactly the same shape regardless of which exception it came from, and the shared code below can make one assumption that always holds.

The seven that push an error code Exceptions 8, 10, 11, 12, 13, 14 and 17. There is no pattern to memorise, it is simply what the architecture specifies. Getting this list wrong shifts the stack by four bytes and the handler reads the wrong interrupt number.

Why assembly stubs exist at all

A reasonable question: why not point the IDT gate straight at a C++ function? Three reasons, and each one is fatal on its own.

So each of the 34 gates points at a small assembly stub. The stub records which interrupt it is, saves the registers, calls into C++, then undoes all of that and returns properly.

The shared stub, line by line

All 34 stubs jump to the same code once they have pushed their number. This is the densest assembly in the project and worth going through carefully.

The [esp + 32] is the piece that trips people up. After pusha has pushed eight 32 bit registers, everything that was on the stack has moved 32 bytes deeper. The interrupt number the stub pushed is now exactly 32 bytes below the top.

The dispatcher in C++

Once the stub has normalised everything, the C++ side is a plain function taking one argument. All the awkwardness stayed in assembly.

Exceptions halt the machine deliberately. There is no meaningful recovery from a general protection fault in a kernel this simple, so the handler prints what happened and stops. That is far more useful than continuing with corrupt state.

Registering everything

idt_init fills 34 of the 256 slots and leaves the rest zeroed. An interrupt arriving on an unregistered slot is a fault in itself, which is worth understanding because it caused a real bug in the lessons.

The bug this caused In lesson 11 the OS triple faulted at boot. The cause was the PIC being told to allow timer interrupts on IRQ0 before slot 32 had a handler. The timer fired, the CPU found an empty gate, raised a fault, failed to handle that too, and reset. The fix was to leave the timer masked until its handler existed. Never unmask an interrupt before its gate is filled in.

The sti instruction

Interrupts stay disabled for the entire setup. Nothing is allowed to fire until the GDT, the IDT and the PIC are all configured, and one instruction opens the gate.

Before sti the CPU ignores hardware interrupts entirely. After it, a keypress can arrive at any moment. Putting it last means the OS is never half configured when the first one lands.
