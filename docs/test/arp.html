Guide / Getting online

ARP

You know a machine's IP address but the network card only understands MAC addresses. ARP is how you ask the network to fill in the gap, and it is the OS's first real conversation with another machine.

The gap ARP closes

Two kinds of address, at two different layers, and neither can be derived from the other.

To send anything you need the destination MAC for the Ethernet header. To decide where you are sending you use an IP address. So there is a lookup missing in the middle, and ARP performs it.

Why it cannot be calculated A MAC is assigned by whoever made the card. An IP is assigned by whoever runs the network. There is no relationship between them, so the only way to learn the pairing is to ask.

Two messages

The whole protocol is a question and an answer. No connection, no handshake, no state.

The request has to be broadcast because you do not yet know who to send it to. That is the problem you are trying to solve, so the only option is to ask everybody.

ARP is local only

An important limit. ARP cannot reach beyond your own network segment, and that is by design rather than a shortcoming.

So how does anything reach the internet? You do not ARP for the distant server. You ARP for your gateway, then send everything destined elsewhere to the gateway's MAC and let it forward onward.

The packet

Twenty eight bytes with a fixed layout. Every field has a fixed offset, which makes building and parsing it straightforward once you have the map.

The first four fields are almost always the same values, describing Ethernet and IPv4. They exist because ARP was designed to work over other kinds of network too, so it declares what sort of addresses it is talking about.

Building a request

Filling in the 28 bytes, with every multi byte field written high byte first.

The one field that is left blank

Bytes 18 to 23 are the target MAC, and in a request they are all zero. That is not an oversight, it is the question itself.

The reply comes back with the same structure but that blank filled in, and with the sender and target roles swapped. So the answer arrives in the sender MAC field of the reply.

The real request, byte by byte

These are genuine bytes captured leaving the card during the lesson. Forty two bytes: the fourteen byte Ethernet header plus the twenty eight byte ARP packet.

And the reply

QEMU's virtual gateway answered. Notice what changed and what stayed the same.

The destination is now our MAC rather than broadcast, because the gateway knows exactly who asked. The operation is 2 instead of 1. And the sender and target fields have swapped roles, so the answer we wanted sits in the sender MAC.

Waiting for the answer

The reply does not arrive instantly, and it arrives among whatever other traffic is on the network. So the code polls and filters.

Where the addresses came from

Two IP addresses are hardcoded in the lessons, and both are conventions of the emulator rather than anything the OS worked out.

A real OS would learn both from DHCP, which is itself a protocol running over UDP. That needs several more layers, so the lessons hardcode the known values and note the shortcut honestly.

It worked first time

Rare enough in this project to be worth recording. The command output matched the packet capture exactly.

Why that gateway MAC looks familiar 52:55:0A:00:02:02 is not random. The last four bytes are the gateway's own IP address, 10.0.2.2, written in hex as 0A 00 02 02. The emulator generates MACs for its virtual devices by embedding the IP, which is a convenient trick for anyone debugging it.

What a real ARP implementation adds

The lessons resolve one address and print it. A full implementation does more, and knowing what is missing matters for the lessons that follow.
