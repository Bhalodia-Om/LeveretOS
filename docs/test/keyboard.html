Guide / Talking to hardware

Keyboard and scancodes

A keyboard does not send letters. It sends a number for each physical key, twice, once when you press and once when you let go. Turning that into typed text is entirely your job.

Keys, not characters

This is the thing to unlearn. The keyboard has no idea what letter is printed on a key. It reports positions on a grid, and the number it sends is called a scancode.

Scancode 0x1E is the key one step right of caps lock. On a US layout that is A. On a French AZERTY layout the same physical key is Q, and the keyboard still sends 0x1E. The layout lives in software, which means the translation table in the lessons is a US layout by choice.

Notice the codes are roughly sequential across each row of the keyboard, because they follow the physical wiring rather than the alphabet. That is why the translation table in keyboard.cpp looks scrambled when you read it as text: it is in keyboard order, not alphabetical order.

Press and release are two separate events

Every key produces two scancodes. The press is called a make code and the release is called a break code, and the relationship between them is a single bit.

Adding 0x80 sets bit 7. So the release code is the press code with the top bit turned on, which means testing for a release is one mask.

The driver ignores most releases. You do not want an A to appear when the key goes down and again when it comes up. But two releases do matter, and they are the shift keys.

Why shift has to be remembered

Shift is not a character, it is a state. The keyboard sends 0x2A when left shift goes down and 0xAA when it comes up, and in between it sends the scancode of whatever else you pressed. The driver has to hold onto that in between state itself.

This is why shift_held is a file scope variable rather than a local. It must survive between interrupts, because each interrupt only sees one scancode and has no memory of the last one.

Making a letter uppercase The driver subtracts 0x20 rather than using a library function. In ASCII the uppercase letters sit exactly 32 below the lowercase ones, so 'a' minus 0x20 is 'A'. It only works for letters, which is why the code checks the range first.

Two ways to get a keystroke

Lesson 3 read the keyboard by polling, and lesson 11 replaced that with interrupts. The difference matters enough that it was worth a whole lesson.

Polling means asking constantly, which burns the CPU doing nothing useful and still misses keys if you are busy elsewhere. Interrupts invert the relationship: the hardware interrupts you when something happens, so the CPU can sleep in between.

What sleeping looks like
while (!line_ready) { asm volatile ("hlt"); // stop the CPU until an interrupt arrives }
hlt halts the processor. It does nothing at all until an interrupt wakes it, which for us means a keypress. Compare that to a polling loop spinning millions of times per second.

Keeping the interrupt handler short

An interrupt handler runs at an awkward moment, interrupting whatever the OS was doing. The longer it takes, the longer everything else is stalled, and other interrupts may be blocked meanwhile.

So the design splits the work. The handler does the minimum and leaves the waiting to ordinary code.

The handler never blocks and never waits. It appends a character and sets a flag. All the waiting happens in read_line, which is normal code that can afford to sit still.

The shared buffer, and why volatile appears

Two pieces of code touch the same variables at unpredictable times: the interrupt handler writes them, and read_line reads them. That is exactly the situation volatile exists for.

Without volatile on line_ready, the compiler looks at the waiting loop, sees nothing inside it that changes the flag, and is entitled to read the value once and loop on that copy forever. The OS would hang on the first keystroke.

The bounds check that prevents a real disaster

The buffer is 128 bytes. If somebody holds down a key and the driver keeps appending, writing past the end would corrupt whatever memory sits after the array, with no warning at all.

The guard, from keyboard.cpp
} else if (line_length < sizeof(line_buffer) - 1) { line_buffer[line_length++] = c; putchar(c); }
The minus one leaves room for the terminating zero byte. Once full, extra keystrokes are silently dropped rather than overflowing. Using sizeof rather than a literal 128 means the check stays correct if the buffer size changes.
No safety net exists here In a normal program a buffer overflow might crash with a clear error. In a kernel there is nothing to catch it. You would overwrite another variable, or the stack, and the symptom would appear somewhere entirely unrelated much later. Bounds checks are not optional at this level.
