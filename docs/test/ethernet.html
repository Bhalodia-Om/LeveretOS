Guide / Getting online

Ethernet frames

Fourteen bytes at the front of every packet that say who it is for, who it is from, and what kind of data follows. Everything above this layer depends on getting those fourteen bytes right.

A frame is a header plus a payload

The card sends and receives raw byte sequences. Ethernet is the agreement about what the first few bytes of that sequence mean, so two machines can understand each other.

That is the whole header. Three fields, fourteen bytes, and then whatever data the higher layer wants to send. ARP packets, IP packets and everything else ride inside that payload.

What the card adds Real Ethernet also has a preamble before the frame and a checksum after it. The card generates and strips both, so the driver never sees them. That is why the lessons' frames start straight at the destination MAC.

MAC addresses

Six bytes identifying a network interface, burned in by the manufacturer. Unlike an IP address, it does not describe where you are, only which card you are.

The card knows its own, which is what the MAC read in the driver lesson was for. The OS stores it once at startup and puts it in the source field of every frame it builds.

Broadcast

One address is special. All six bytes set to 0xFF means every machine on the local network should accept the frame.

That is what makes ARP possible. You cannot address a machine whose MAC you do not know yet, so you shout to everyone and wait for the right one to answer.

The EtherType

Two bytes saying what kind of data is in the payload. Without it the receiver would have to guess, and there would be no way to run several protocols over the same wire.

These values are assigned by a standards body, so every machine agrees. The lessons define two, one for ARP which is used now, and one for IPv4 which the next lesson will need.

Byte order matters here

The EtherType is the lessons' first real encounter with network byte order, and getting it backwards fails silently.

High byte first, always, for every multi byte field inside a packet. That is the opposite of the hardware register convention from the byte order page, where the low byte goes first.

Why a layer at all

Before this lesson the shell built a frame header by hand, inline, byte by byte. That works once and becomes a liability immediately after.

So the lesson introduces two functions that own the header. Everything above them passes a destination, a type and a payload, and never touches byte 12 again.

Sending

Building a frame is filling in three fields then copying the payload after them.

Receiving

The reverse: take a raw frame from the driver, pull the header apart, and hand the caller the pieces it needs.

The interesting part is the third parameter. Rather than copying the payload into a caller supplied buffer, the function points the caller at its own internal buffer, which avoids a copy entirely.

What this layer leaves out

Keeping it small was the point. Several things a real stack would handle are absent, and knowing which ones stops them becoming surprises.

checking the destination MAC on receivethe card filters most of it in hardware, but the layer hands up anything that arrives without verifying it was addressed to us
dispatching by EtherTypethe caller checks the type itself. With only ARP in use that is fine, and a real stack would route to a registered handler
a queue of received framesone static buffer, reused each call. The caller must finish with the payload before calling receive again

The layer exists so ARP and later IP do not each reimplement the header. It does that job in about forty lines, which is the right size for what it is.
