Byte order

A number bigger than one byte has to be stored as several bytes. Nobody ever agreed on which end goes first, and that disagreement is now permanent.

The problem

The value 0x1234 needs two bytes: 0x12 and 0x34. If you are storing it at memory address 100, which byte goes at 100 and which at 101?

Both answers are defensible, and both were chosen by different hardware designers. There is no winner, only a convention you have to know for whichever thing you are talking to.

OrderAddress 100Address 101Who uses it
Little endian0x340x12x86 CPUs, so your whole OS
Big endian0x120x34network protocols, so every packet

Little endian means the little end, the least significant byte, comes first. Big endian means the big end comes first. Big endian matches how humans write numbers, which is why it feels more natural, and it is also why network designers picked it.

Why your CPU being little endian rarely matters

Inside your own program, byte order is invisible. When you write uint16_t x = 0x1234; and read x back, you get 0x1234. The CPU stored it backwards in memory and read it back backwards, so the two cancel out.

It becomes visible the moment bytes leave your program and land somewhere that has its own opinion. That happens in two places in the lessons, and they pull in opposite directions.

Case one, hardware registers want the low byte first

Most of the chips in the lessons are 8 bit era designs with 8 bit registers. To give them a 16 bit number you write it in two halves, and they almost always want the low half first.

The timer lesson does exactly this. The PIT command byte even contains a setting that says "the divisor is coming as two writes, low byte first", which is bits 5 to 4 of 0x36. The chip is telling you the order it expects.

From the timer
outb(PIT_CHANNEL0, (uint8_t)(divisor & 0xFF)); // low byte outb(PIT_CHANNEL0, (uint8_t)((divisor >> 8) & 0xFF)); // high byte
Mask for the low byte, shift then mask for the high byte. Two writes to the same port.

The NE2000 driver follows the same shape everywhere it deals in 16 bit values, though it uses two separate ports rather than writing twice to one. RBCR0 takes the low byte of the DMA byte count and RBCR1 takes the high byte. The 0 and 1 suffixes are a naming convention meaning low and high.

Case two, network packets want the high byte first

Now the opposite. Every multi byte field in a network packet is big endian, high byte first. This is so universal it has a name, network byte order.

The reason is practical. Two machines with different CPU designs need to exchange packets and agree on what the bytes mean. Rather than negotiate, the protocol designers fixed one order forever. Since the internet grew up on big endian machines, big endian won.

From the Ethernet layer
frame[12] = (ethertype >> 8) & 0xFF; // high byte FIRST frame[13] = ethertype & 0xFF; // low byte second
Compare this to the timer code above. Same operators, opposite order. That is the whole difference between hardware order and network order.

Reading a field back reverses the process. You take the first byte, shift it up into the high position, and OR the second byte underneath it.

Reading it back
*ethertype_out = ((uint16_t)rx_frame[12] << 8) | rx_frame[13];
Byte 12 becomes the high half, byte 13 the low half. The cast to uint16_t matters, without it the shift could overflow an 8 bit value and lose the byte entirely.

Seeing it in a real captured frame

Here are the actual bytes the OS put on the wire during the ARP lesson, taken from a packet capture. Hover a field to see where it sits.

Look at the EtherType, 08 06. The value is 0x0806 and the bytes appear in that same visual order, high byte first. If the OS had written it little endian you would see 06 08 and every machine on the network would read it as 0x0608, which means nothing. The frame would be silently ignored.

The failure mode is silence Getting byte order wrong in a packet does not crash anything. The receiving machine reads a field it does not recognise and drops the frame. You see nothing at all, which makes it one of the harder bugs to chase. The lesson overview flags it as the classic networking mistake for good reason.

A rule of thumb

When you are writing to a chip, check the datasheet, and expect low byte first. When you are building a packet, always high byte first, no exceptions. If you are ever unsure which side you are on, ask whether the bytes are about to leave the machine.
