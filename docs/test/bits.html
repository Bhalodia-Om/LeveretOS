Bits, bytes and hex

Hardware does not deal in numbers the way your programs do. It deals in individual wires that are on or off. This page is how you read that.

A byte is eight switches

A bit is one switch: on or off, 1 or 0. A byte is eight of them side by side. That is the whole idea. Everything else on this page is notation for describing which switches are on.

Bits are numbered from the right, starting at zero. The rightmost bit is bit 0, the leftmost in a byte is bit 7. That feels backwards until you see why: bit 0 is the ones column, bit 1 is the twos column, bit 2 is the fours column. Bit n is worth 2 to the power of n, so numbering from the right keeps the maths tidy.

Try this Turn on bit 1 and bit 3 above. You get 2 + 8 = 10, which is 0x0A in hex. Every hex value in the lessons is just a set of switches like this.

Why hex instead of decimal

Decimal hides the bits. The number 154 tells you nothing about which switches are on. Hex shows them, because one hex digit is exactly four bits. Always. That fixed relationship is the entire reason hardware documentation is written in hex.

A four bit group is called a nibble, half a byte. So a byte is two hex digits, and you can read each half independently. 0x9A is nibble 9 (1001) then nibble A (1010). Put together: 1001 1010. You never have to do division to convert, you just look up each digit.

That is why the lessons use 0x numbers everywhere. 0xFF is obviously all eight bits on. 255 is not obviously anything.

Masking with AND

The & operator compares two numbers bit by bit. A result bit is 1 only if both input bits were 1. On its own that sounds abstract, so here is what it is actually for: keeping some bits and throwing the rest away.

Say you have a 16 bit value and you only want the bottom eight bits. You AND it with 0xFF, which is 11111111. Any bit lined up with a 1 survives unchanged. Any bit lined up with a 0 becomes 0. So the bottom byte passes through and everything above it is erased.

What masking looks like
0x0806 = 0000 1000 0000 0110 & 0x00FF = 0000 0000 1111 1111 --------------------- result = 0000 0000 0000 0110 = 0x06
The high byte 0x08 got masked away. Only the low byte 0x06 is left.

This pattern shows up constantly in the lessons, because hardware registers are often eight bits wide while the values you want to put in them are wider. You will see value & 0xFF every time a 16 bit number has to be squeezed into an 8 bit port.

Common masks worth memorising 0x0F keeps the low nibble. 0xF0 keeps the high nibble. 0xFF keeps one byte. 0xFFFF keeps two bytes. Fs keep, zeros erase.

Setting with OR

| is the opposite tool. A result bit is 1 if either input bit was 1. You use it to turn bits on without disturbing the others.

This is how the lessons combine flags. In the paging code a page table entry is built with (i * 0x1000) | PAGE_PRESENT | PAGE_WRITABLE. The address provides the high bits, then each OR switches on one more flag in the low bits. Nothing already set gets lost.

Shifting

<< and >> slide bits left or right. Shifting left by one doubles the number, shifting right by one halves it, because every bit moves one column over. But in hardware code you rarely care about the arithmetic. You are moving bits to a specific position.

1 << 5 means "a single 1 bit, parked in position 5". That is 0010 0000, or 0x20. It is the standard way to build a mask for one specific bit, and it reads much better than writing 0x20 and hoping the reader counts correctly.

The other big use is pulling a piece out of a wide value. To get the high byte of a 16 bit number, shift it right by 8 so the high byte lands in the low position, then mask with 0xFF to trim anything else. That combination, (v >> 8) & 0xFF, appears all over the networking code.

The 1 versus 1u trap In the PMM you will see 1u << (frame % 32) with a u. Shifting a plain 1 into bit 31 is technically undefined behaviour in C++, because bit 31 is the sign bit of a signed int. The u makes it unsigned, where bit 31 is just another bit. It never bites you until it does, so the lessons write 1u whenever a shift might reach that far.

Clearing a bit, the NOT trick

Turning a bit off takes two operators. You cannot AND a bit away directly, because AND needs a mask with a 0 in exactly one position and 1s everywhere else. Building that by hand is awkward, so you build the opposite and flip it.

~ inverts every bit. So 1u << 5 gives you 0010 0000, and ~(1u << 5) gives you 1101 1111, which is exactly the mask you want: zero in position 5, ones everywhere else. AND with that and bit 5 is cleared while the rest pass through untouched.

The three bit operations from the PMM
// turn bit on frame_bitmap[frame / 32] |= (1u << (frame % 32)); // turn bit off frame_bitmap[frame / 32] &= ~(1u << (frame % 32)); // test bit frame_bitmap[frame / 32] & (1u << (frame % 32));
Set, clear, test. Once these three read naturally, most low level code stops looking cryptic.
