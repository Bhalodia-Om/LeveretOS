Guide / Talking to hardware

Port I/O

The screen was memory you could write to. Most other devices are not. They live in a separate numbered space that needs its own CPU instructions, and that difference shapes every driver in the project.

Two completely separate address spaces

An x86 CPU has two ways to reach the outside world, and they do not overlap. Memory addresses are one space, I/O ports are another. Address 0x60 in memory and port 0x60 are unrelated places.

This is why you cannot reach the keyboard with a pointer. There is no address you can cast and dereference, because the keyboard is not in the memory space at all. The only way in is the in and out instructions, and C++ has no syntax for those.

Why two spaces exist The original 8086 had a small memory space and devices were scarce, so giving peripherals their own 65536 port numbers kept them out of the way of RAM. Later designs mostly abandoned this in favour of memory mapping, which is why modern cards use memory mapped registers. The devices in these lessons are old enough to use ports.

The four functions

io.h contains four tiny functions and nothing else. They are the only doorway between the OS and every port based device it touches.

The suffix is the width: b for byte, l for long meaning 32 bits. There is a 16 bit inw and outw too, but the lessons never needed it.

Reading the inline assembly

These functions are the first inline assembly in the project, and the syntax is dense. It is worth taking apart once, because after this it repeats with small variations.

The three colon separated groups are the structure: instruction, then outputs, then inputs. The quoted letters are constraints telling the compiler which register each value must live in, because the in instruction is picky about that.

Same constraint, different register

Comparing inb and inl side by side raises an obvious question. They use the identical constraint "=a", so how does one produce 8 bits and the other 32?

The answer is that "a" means the accumulator register, which has three names depending on how much of it you use. They are all the same physical register, just different sized windows onto it.

The compiler picks the name from the variable's type. A uint8_t result means AL, a uint32_t result means EAX. The instruction mnemonic already fixes the transfer width, and the constraint just has to agree with it, which it does automatically.

Why volatile appears here too

Every one of these functions marks its assembly volatile. Without it the compiler would be free to optimise the instruction away.

Consider reading the keyboard port twice in a row. To the compiler, inb(0x60) is a function that takes 0x60 and returns a value, with no visible side effects. Called twice with the same argument, it should give the same answer, so why do it twice?

But reading the keyboard port actually consumes a scancode from the controller. The second read returns something different, and skipping it loses a keystroke. volatile is how you tell the compiler this instruction matters even when its result looks predictable.

The pattern to remember Anything that touches hardware needs volatile: port I/O, memory mapped registers, and variables shared with interrupt handlers. All three appear in the lessons and all three break in confusing ways without it.

A port is often a window, not a value

The most useful mental shift on this page. You might expect each port to hold one value, like a variable. Many do not. Instead, one port selects what you are talking about and a second port carries the data.

The RTC is the clearest example. There are dozens of fields inside the clock chip, but only two ports.

So port 0x71 does not hold the seconds, or the hours, or anything fixed. It holds whatever field you last selected through port 0x70. The pair together behave like an array index and an array element.

This address plus data pattern shows up three more times in the lessons, and recognising it makes each new device much less mysterious.

Base plus offset

One more pattern, used heavily by the NE2000 driver. A device gets a block of consecutive ports, and the driver stores the first one then adds a fixed offset for each register.

The base is not known at compile time, it is read from the PCI configuration at boot, which is why it lives in a variable rather than a #define. The offsets are fixed by the chip design, so those are constants. Every register access is the variable plus a constant.

From the NE2000 driver
static uint16_t io_base = 0; // filled in from PCI at boot #define NE_CR 0x00 // command register #define NE_ISR 0x07 // interrupt status #define NE_DATA 0x10 // the remote DMA data window // every access is base plus offset: outb(io_base + NE_CR, CR_STOP | CR_PAGE0); uint8_t status = inb(io_base + NE_ISR);
If io_base were wrong, every register access would land on some other device's ports. That failure mode is covered on the PCI page.

Where the network card differs Every port above is a fixed number. The NE2000's ports are not, because it is a PCI card and the firmware assigns it a block at boot. That is the whole reason the PCI scan exists: to find out where the card ended up before you can talk to it.
